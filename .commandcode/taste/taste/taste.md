# Taste
- When resuming work (e.g. user says "continue"), reconstruct state first before changing anything: read working notes (`prompt.md`, `context.md`), check `git status`/`git log` (README diffs may document the plan), and compare file mtimes + prior screenshots in `scratch/` to pinpoint where the last session stopped. Confidence: 0.75
- User delegates whole tasks and expects autonomous carry-through to completion — pick up state, finish the work, verify, and report — without check-ins. Confidence: 0.6
- After UI changes, verify visually with real rendered screenshots (full-page plus section crops, saved under `scratch/`) and HTML/curl checks; finish with `npm run build` passing before declaring done. Clean up scratch intermediates afterward, keeping only the final `verify_*.png` captures. Confidence: 0.8
- For browser screenshots, drive headless Chrome directly (`"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new --disable-gpu --hide-scrollbars --window-size=… --virtual-time-budget=… --screenshot=…`). `agent-browser` is not installed and `ego-browser`'s high-level helpers (`openOrReuseTab`, `captureScreenshot`, etc.) are unavailable in the current install — don't spend turns probing them. Confidence: 0.8
- macOS `sips` gotcha: `--cropOffset 0` falls back to a center crop; use a nonzero offset (e.g. `1`) to anchor crops at the top when slicing full-page screenshots into section bands. Confidence: 0.7
- Site is bilingual: Tamil at `/` (`app/(ta)/`), English at `/en/`; every page/feature must be built in both languages with parallel structure and paired data fields (`*Ta` / `*En`). Confidence: 0.9
- UI is plain CSS built on the token system in `app/theme/foundation.css` (`--accent`, `--gold`, `--kumkum`, `--leaf`, `--tamil` font, etc.) and the `portal-*` section conventions — reuse existing tokens and patterns instead of introducing frameworks or ad-hoc colors. Confidence: 0.85
- When the user supplies a spec/requirements document (e.g., the IA/product spec), treat it as the source of truth: audit the current build against it section by section first, report what already conforms, implement the highest-value gaps in one pass, and explicitly list the larger items as deferred rather than attempting everything at once. Confidence: 0.7
- Content rigor matters: historical/biographical claims must be verifiable — source-tagged against the sources ledger (S1–S40) with confidence levels (High / Medium-High / Single-source); prefer evidence-backed copy over unsourced statements. Confidence: 0.8
- Keep design plain and credible: no performative cultural/patriot theming or symbolic showcase features (explicitly rejected e.g. an Ainthinai five-landscapes kurinji/mullai/marutham/neythal/palai explorer). The site must serve its archival purpose plainly — minimal ornamentation, factual presentation over identity display. Confidence: 0.9
- Accessibility is an explicit requirement (WCAG compliance): semantic markup, `aria-*` labels, visually-hidden headings, and keyboard/focus-friendly controls in all UI work. Confidence: 0.65
- Responsive targets for this site: desktop 1440px (1280px max container, multi-column grids, sticky sidebars), tablet 768px (collapsible/off-canvas drawers), mobile 375px (single-stack, sticky reader bottom bar, swipeable filter chips) — new surfaces must work at all three breakpoints. Confidence: 0.7
- For redesigns the user grants full creative latitude ("surprise me" — agent picks the direction) but sets one hard constraint: the new design must follow the site's existing content and purpose; the design adapts to the content, content is never rewritten or dropped to fit a new look. Confidence: 0.75
- When the user asks for a redesign "from scratch" / "no resemblance to current design", they want a complete visual departure — new palette, typography, and layout language, not incremental restyling. For that task this supersedes the reuse-existing-tokens preference; content inventory, bilingual parity, and accessibility still apply unchanged. Confidence: 0.8
- Bias strongly toward executing over recon: the user loses patience when many consecutive turns are spent on read-only exploration/planning before any output is produced. Two explicit data points: after a long design-mapping phase ("i said redesign from scratch i still see same design"), and again after a multi-turn research pass for the `fresh.md` handover brief that ended without the file being written ("wheres fresh.md"). Even when the deliverable IS a research-backed brief, the turn must end by actually writing the file and reporting its full path — never stop at the research stage. Keep investigation tight, write changes/deliverables early, and verify as you go. Confidence: 0.85
- When dissatisfaction with a design is strong, the user prefers a clean-slate restart in a NEW folder over iterating in place: produce a single consolidated handover brief (e.g. `fresh.md`) that carries over everything substantive — content holdings, data schemas, research state, requirements, and a "don't port" list for unrelated cruft — while explicitly EXCLUDING design/UI details. This extends (not replaces) the "redesign from scratch = full visual departure" learning. Confidence: 0.85
- For handover/knowledge-capture briefs, ground every claim in actual project artifacts (project docs, data-layer exports, content frontmatter, research ledgers, asset listings) — build a complete holdings inventory with real metadata extracted from files rather than summarizing from memory. Confidence: 0.8
- The user explicitly signals desired depth per task ("think slow and include all"): exhaustive completeness outranks speed when the deliverable is a comprehensive brief — but keep fast-execution behavior for build/redesign tasks. Confidence: 0.85
